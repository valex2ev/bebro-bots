# Постановка: Telegram-боты с ИИ (bebro-bots)

Документ фиксирует согласованные требования и ограничения. Реализация — по отдельной команде.

## 1. Цель

Несколько независимых Telegram-ботов (минимум два экземпляра), каждый общается в группах с помощью LLM, хранит персистентные данные локально, поддерживает настройку через диалог и технические команды для обслуживания.

**Окружение:** только Windows-сервер. Публикация в интернет — через Cloudflare Tunnel (внешний URL сообщается отдельно).

**Стек:** Python или Node.js (выбор при старте реализации).

**GitHub:** проект ведётся в репозитории на GitHub.

---

## 2. LLM и инструменты

- Провайдер: **OpenAI API** (параметры подключения — в конфигурации/переменных окружения, не в коде).
- Нужны **tools / function calling** для полноценного общения: вызовы функций на сервере (память, настройки, чтение/запись предпочтений и т.д.), чтобы факты не «висели» только в промпте.
- **Поиск в интернете:** провайдер **Tavily** (`POST https://api.tavily.com/search`), ключ **`TAVILY_API_KEY`** в `.env`. Режим задаётся в конфиге **`web_search.mode`**: **`on_trigger`** — инструмент **`web_search`** в tools **только** если в тексте входящего сообщения (текст или подпись) есть подстрока **`найди`** (регистр не важен); **`always`** — **`web_search`** доступен в каждом ответе на **сообщение группы** (инициатива бота и проактивные реакции по-прежнему **без** поиска). Триггерная подстрока в коде — константа **`WEB_SEARCH_TRIGGER`** в `triggers.py` (по умолчанию `найди`). Явное цитирование источников в ответе пользователю **не** требуется, если об этом не просили; опирайся на результаты поиска для проверяемых фактов.
- **Глобальные лимиты (UTC):** в SQLite таблица **`global_usage_daily`** — накопление **prompt (input) токенов** ко всем вызовам `chat.completions` и числа **успешных** запросов Tavily; лимиты **`limits.daily_input_tokens`** и **`limits.daily_web_searches`** (сумма по **всем ботам и чатам**). Календарные сутки — **UTC** (`use_utc_calendar_day`, иначе не используется). При исчерпании лимита токенов или поиска — короткое сообщение в чат-триггер с антиспамом (**`limit_notify_cooldown_minutes`** на пару чат + тип лимита).
- **Джиттер ответа:** **`response_jitter_ms_min`** / **`response_jitter_ms_max`** — задержка перед основным запросом к модели на **обычное** сообщение группы; в коде — **`asyncio.sleep(random.uniform(jmin, jmax) / 1000)`** (непрерывное **равномерное** распределение на отрезке **[jmin, jmax]** миллисекунд, концы включительно). После задержки заново читается окно **`recent_messages`**. Политика «хвоста чата» после исходного сообщения — §16 (к реализации). Команды **`/bebro_ping`**, **`/bebro_params`**, админские — без джиттера.
- **Контекст в промпте:** последние N **`long_memory`** и M **`situation_rules`** (лимиты YAML) явно добавляются в пользовательский блок; инструменты **`remove_long_instruction`**, **`remove_situation_rule`** удаляют записи по **id** (см. **`get_group_state`**: `long_instructions_with_ids`, `situation_rules_with_ids`). **`reply_probability`** задаётся **только** в корневом YAML, не через **`set_preference`** и не из БД.
- **Изображения (vision):** фото из Telegram скачиваются ботом и передаются в OpenAI в **первом пользовательском сообщении** текущего хода как один или несколько `image_url` (data URL, base64). Нужна **модель с поддержкой входа изображений** (например GPT‑4o‑семейство). В конфиге блок **`vision`**: `enabled`, `max_image_bytes`, **`max_images_per_turn`** (максимум изображений за один запрос к модели). **Всегда** передаются: **фото во входящем сообщении**; **фото из сообщения, на которое сделан reply** (если там есть фото). **Фото из более ранних сообщений чата** (по `photo_file_id` в SQLite, в пределах окна истории и лимита кадров) передаются **только** если по тексту/подписи текущего сообщения распознан явный запрос на действие с картинкой из переписки (прокомментировать «фото выше», «что на той картинке в чате», оценить изображение из ранних сообщений и т.п.) — эвристика **`text_asks_prior_chat_images`** в `telegram_vision.py`. Иначе старые картинки в контексте только как текст `[фото]` и подпись, без загрузки пикселей. Инициатива бота — без фото из истории; проактивная реакция на выбранное сообщение — пиксели **только** этого сообщения (`history_photo_policy`: `never` / `if_text_asks` / `explicit`).
- Блок **новости и RSS-ленты** как отдельный модуль — по-прежнему вне скоупа; поиск по запросу пользователя — через Tavily, см. выше.

## 3. Группы и видимость

- Боты могут быть в **разных группах**.
- Политика: отвечать и инициировать активность **только в чатах, куда бот добавлен** и откуда приходят апдейты (технически бот не пишет в произвольные чаты без участия в них).
- При необходимости — явный **whitelist `chat_id`** (игнор прочих апдейтов).

---

## 4. Когда бот реагирует

**Явное обращение** (в одном сообщении может быть несколько) — откликаются **только** боты, к которым обратились; остальные экземпляры сообщение **игнорируют** (без случайного ответа):

- **`@username` бота** — по сущностям Telegram (**`MessageEntity`**: mention / text_mention), не по поиску подстроки в тексте. Учитываются **текст** и **подпись к фото** (`entities` / `caption_entities`).
- **Текстовый алиас** — подстрока из БД **`chat_aliases`** (пара бот+чат), совпадение **без учёта регистра**, но **не** считается обращением, если вся совпадающая подстрока целиком лежит **внутри кавычек**: ASCII `"`/`'`, типографские `«»`/`""`/`''`, обратные `` ` `` — пара открывающий/закрывающий; внутри допускаются пробелы по краям строки алиаса.
- **Reply** на сообщение **бота** — явное обращение к автору того сообщения (по `username` или по `user_id`, зарегистрированному при старте через `get_me`).

Если в сообщении **нет** ни одного явного обращения — одна вероятность **`reply_probability`** из **корневого YAML** (по умолчанию **~0.15**); из БД и через **`set_preference` не переопределяется**. Плюс реакции и инициатива по другим правилам.

Инструмент **`add_chat_alias`** / **`remove_chat_alias`**: если в сообщении есть `@username` **другого** бота из конфига и **нет** `@username` текущего — мутации алиаса недоступны (см. `chat_aliases_policy`). Общие обращения без @ ботов («парни», «ребята») — каждый бот может сохранить у себя. Не `@username` людей и не логины Telegram (ASCII); «называть участника так-то» — **`long_memory`**.

| Ситуация | Поведение |
|----------|-----------|
| **Явные указания** (пореже/почаще, покороче/поподробнее и т.п.) | Отдельная логика: **распознавание → сохранение в БД** как **долговременные предпочтения**, не только текст в промпте. |

## 5. Форматы ответа

- **Реакции:** обычные emoji-реакции на сообщения **без** обязательного текстового ответа (только реакция), когда так решено логикой.
- **Ответы на сообщения** (когда бот всё же отвечает): допустимы **текст**, **один или несколько emoji**, **стикер** — по решению модели/правил.

---

## 6. Стикеры

- **Основной источник:** стикеры, которые «крутятся в группе» — накопление **`file_id`** (и при необходимости метаданных набора) из **входящих** сообщений в SQLite.
- **Дополнительно:** собственные наборы через **BotFather** (`getStickerSet` и выбор стикеров из привязанных к боту паков).
- Ограничение Telegram: полный каталог чужого набора без участия пользователей недоступен; поведение «как у людей» достигается через **накопление увиденных** стикеров.

## 7. Персона и настроение

- У каждого бота — **базовое текстовое описание личности** в SQLite (`bot_state.persona_text`), задаётся и меняется через LLM-инструмент **`set_bot_persona`** и отображается в промпте. В YAML конфигурации **нет** поля personality; стартовый текст при пустой БД — нейтральный шаблон в коде.
- **Настроение** (`bot_state.mood`) — глобально на экземпляр бота; меняется инструментом **`set_mood`**, иногда **случайно** фоновой задачей (без LLM).
- **Тон общения** задаётся **по чату** числовыми осями в настройках чата (см. §15): теплота, острота, тревога, радость vs грусть, ирония, пафос, скептицизм, цинизм, уверенность, апатия, игривость — значения **−1 / 0 / 1**. Поверх базы чата применяется **временный сдвиг** `tone_drift_json` в `bot_state` (случайные небольшие изменения фоновой задачей).
- Просмотр текущих параметров в чате: команда **`/bebro_params`** (доступна участникам группы): модель OpenAI, режим **`web_search.mode`**, **потрачено/лимит** по input-токенам и web search за текущие сутки UTC, прочие параметры. В группе с **несколькими** ботами используйте форму **`/bebro_params@username_бота`**, чтобы команда обработал нужный экземпляр; при одном боте достаточно **`/bebro_params`**.

## 8. Память и контекст

- **Хранилище:** SQLite (один или несколько файлов на сервере) + при необходимости JSON для мелочей.
- **История чата:** Bot API **не** отдаёт произвольную историю группы; контекст строится из того, что бот **получил в апдейтах** и сохранил.
- **Скользящее окно** последних сообщений по каждому чату — хранить в SQLite по мере поступления; **размер окна настраиваемый** (в т.ч. из чата), **не зашит в код**.
- **Предпочтительно:** опора на **сжатый контекст** (саммари/сжатие) + ограниченное число последних реплик — параметры настраиваемые. Частота случайного обновления саммари — **`conversation_summary`** в YAML (`min_messages_in_window`, `random_summarize_probability`).

- **Долговременные данные:** инструкции от участников (`long_memory`, в т.ч. **как называть людей** — не путать с алиасами), **ситуационные правила** (`situation_rules`: триггер «когда» + инструкция «как вести себя»), **текстовые алиасы** (`chat_aliases`: по **`bot_id` + `chat_id`**; при совпадении подстроки — обязательный отклик у этого бота; **без** `@username` людей и без «логинов» Telegram; при старте БД чистятся ошибочные записи; при миграции со старого формата строки дублируются по `bot_id` из `chat_messages`), частота инициативы, предпочтения по длине/частоте (`verbosity`, `frequency`, `response_depth`: shallow|normal|deep), **проактивные реакции** (`proactive_reaction_probability`), привязки к стикерам и т.п.
- **Восприимчивость к пожеланиям:** параметр конфига **`feedback_sensitivity`** (целое **1…5**, по умолчанию **4**) — влияет на формулировки в системном промпте об «уровне учёта» деталей; **объём** `long_memory` и `situation_rules` в контексте задаётся отдельно блоками **`long_memory`** и **`situation_rules`** в YAML (`retention_days`, `context_limit`, для правил ещё `max_stored`).

## 9. Настройки

- **Основной путь:** изменение настроек **естественным языком в чате** (с извлечением намерения и записью в БД). Удаление текстового алиаса — через **`remove_chat_alias`** (например просьбы «перестань откликаться на …», «убери алиас …»); модель передаёт в инструмент саму подстроку-триггер.
- **Кто может менять:** **любой участник группы** (без ограничения админами — осознанный риск, принят заказчиком). Запись предпочтений и правил через инструменты **не применяется к сообщениям от других ботов** (`from_user.is_bot`).
- **Технические действия** (сброс памяти, перезапуск и т.п.) — **узкий набор команд** для администрирования (детализация при реализации).

- Основной язык общения: **русский**; допустимо **немного английского** в ответах при уместности.

## 11. Транспорт Telegram: long polling и webhook

- **Разработка и локальные тесты:** **long polling** (публичный URL не требуется).
- **Прод:** после появления публичного URL (Cloudflare Tunnel) — переключение на **webhook**.
- **Один HTTP-порт** на процесс; несколько ботов — **разные пути** на одном порту (например `/hook/<bot_id>`). Отдельный порт на каждого бота **не обязателен**.

## 12. Конфигурация и секреты

- Параметры LLM, токены ботов, пути к БД — в **конфиге и/или `.env`**, не в репозитории.
- Персона бота **не** задаётся в YAML; опционально **`feedback_sensitivity`** (1–5), **`reply_probability`** (0…1, только YAML, см. §4), **`limits`**, **`response_jitter_ms_*`**, **`limit_notify_cooldown_minutes`**, **`conversation_summary`**, блоки **`long_memory`**, **`situation_rules`**, **`web_search`**, **`vision`**.
- Опционально **`vpn_watch`** (корневой блок конфига): периодическая проверка доступности **Telegram Bot API** и **OpenAI API**; при сбое — до **`reconnect_max_attempts`** раз перезапуск службы Windows (**`Restart-Service`** по **`windows_service_name`**), пауза **`post_restart_wait_seconds`** после каждого рестарта, затем проверка канала; при неудаче — следующая попытка рестарта без дополнительной паузы между циклами. Уведомления о восстановлении или неудаче рассылает бот с **`notify_bot_id`** (один из `bots[].id`) **во все чаты**, для которых в SQLite есть записи в **`chat_messages`** у этого бота (служебный **`chat_id=0`** не используется); отдельный `notify_chat_id` в конфиге **не задаётся**. Фоновая задача регистрируется **только** у экземпляра **`notify_bot_id`**. Работает **только на Windows** (`sys.platform == win32`). Поле **`service_exe_path`** справочное (в коде перезапуск по имени службы). Учётная запись процесса должна иметь право перезапускать указанную службу.
- **Токены и ключи не коммитить** (`.gitignore` для `.env` и локальных sqlite).

## 13. Открытые пункты для уточнения при реализации (низкий приоритет)

- Модель OpenAI по умолчанию и **разные модели на бота** — в конфиге.
- Детальный список **tools** (функций) и политика саммаризации.
- Точный список **админ-команд** и кто может вызывать перезапуск (если отличие от «любой участник» только для техкоманд — уточнить).

## 14. Критерий готовности первой версии (MVP)

- Два бота из конфига, группы, whitelist/политика чатов.
- OpenAI + tools для памяти/настроек.
- Логика упоминаний/reply/случайности/предпочтений из БД.
- Реакции и ответы (текст / emoji / стикер), пул стикеров из группы + опционально свои наборы.
- SQLite: окно сообщений, сжатый контекст (насколько возможно в MVP), долгие предпочтения.
- Long polling; подготовка к webhook на одном порту.

## 15. Реализация (актуализация по коду)

| Пункт | Решение |
|--------|---------|
| Стек | **Python 3.11+**, `python-telegram-bot` (async / v21+), `openai` (AsyncOpenAI), FastAPI + uvicorn для webhook. |
| Явные обращения | Модуль **`addressing`**: `collect_explicitly_addressed_bot_ids` — entities, алиасы вне кавычек (`quoted_spans_excluding_content`), reply на бота; при старте **`register_bot_user_id`** после `get_me`. Если множество непустое — отвечают только перечисленные боты; иначе **`decide_stochastic_engagement`**. |
| Запуск | `python -m bebro_bots` или `python -m bebro_bots polling` — long polling для нескольких ботов в отдельных потоках; `python -m bebro_bots webhook` — один HTTP-порт, пути `/hook/<id>` где `id` — поле `bots[].id` в YAML. |
| Конфиг | `config.yaml` (локально, не в git; при отсутствии читается `config.example.yaml`). Секреты: `.env`. Путь к БД: `sqlite_path`. **`feedback_sensitivity`**, **`reply_probability`** (только YAML). **`limits`**: `daily_input_tokens`, `daily_web_searches`, `use_utc_calendar_day`. **`response_jitter_ms_min`**, **`response_jitter_ms_max`**, **`limit_notify_cooldown_minutes`**, **`conversation_summary`**. **`long_memory`**, **`situation_rules`**, **`web_search.mode`**, **`vision`** (`max_images_per_turn` и др.). Персона — БД §7. Опционально **`vpn_watch`**. |
| Админы | `admin_user_ids` в YAML — целые user id и/или **`"@username"`** в кавычках (YAML); плюс **`ADMIN_USER_IDS`** в `.env` (только числа, через запятую). Команды `/bebroadmin_reset`, `/bebroadmin_status` — только для этих пользователей. |
| Команды в группе | `/bebro_ping`, **`/bebro_params`**, **`/bebro_params@username_бота`** (последний непустой фрагмент после `@`, в т.ч. при опечатке `@@`); без `@` в группе с несколькими ботами команду обрабатывают **все** боты — для одного ответа укажите `@username`. То же для **`/bebroadmin_*`**. Реализация: **`command_is_for_this_bot_username`**. Если задан **`allowed_chat_ids`** и чат не в списке — на перечисленные команды ответ **`Access denied`**. |
| Инструменты LLM | `get_group_state`, `set_preference` (без **`reply_probability`**), `add_long_instruction`, **`remove_long_instruction`**, `add_situation_rule`, **`remove_situation_rule`**, **`set_bot_persona`**, `set_mood`, `update_conversation_summary`, **`add_chat_alias`**, **`remove_chat_alias`**, опционально **`web_search`**, **`complete_turn`**. Запись от ботов — заблокирована. |
| Поиск в сети | Ключ **`TAVILY_API_KEY`**. Учёт успешных вызовов в **`global_usage_daily`**; лимит **`limits.daily_web_searches`**. Режим **`web_search.mode`**. Инициатива и проактив — без поиска. |
| Инициатива | Фоновая задача JobQueue каждые **180** секунд с проверкой вероятности и интервала из настроек чата (`initiative_probability`, `initiative_interval_minutes`). |
| Проактивные реакции | JobQueue каждые **120** с: с вероятностью из `proactive_reaction_probability` (с учётом `feedback_sensitivity`) — одна emoji-реакция на недавнее сообщение **человека** (без текстового ответа). |
| Случайный тон/настроение | JobQueue каждые **600** с: с вероятностью, зависящей от `feedback_sensitivity`, обновляется `tone_drift_json`; иногда меняется `mood` (без LLM). |
| Стикерпаки бота | Поле `sticker_set_names` у бота в YAML — при старте вызывается `getStickerSet`, стикеры кладутся в БД с `chat_id=0` и участвуют в случайном выборе вместе с групповыми. |
| Саммари | Параметры **`conversation_summary`**; отдельный вызов модели; учёт input-токенов в глобальном лимите. |
| Фото в чате | Обработчик принимает **`filters.PHOTO`**. В SQLite для сообщения сохраняются `content_type=photo`, `photo_file_id`, подпись в `content`. В multimodal-запрос: фото текущего сообщения и фото у **reply_to_message** (если есть); фото из окна SQLite — только при срабатывании **`text_asks_prior_chat_images`** (см. §2). Инициатива: **`history_photo_policy=never`**. Проактивная реакция: **`explicit`** по одному целевому сообщению (до одного кадра). Лимит кадров — **`max_images_per_turn`**. |
| VPN (Windows) | Фоновая задача JobQueue по **`vpn_watch.check_interval_seconds`** (только у бота **`notify_bot_id`**): проверка `get_me` + `models.list()`; при сбое — **`Restart-Service`**; после успеха — рассылка во все **`chat_id`** из **`chat_messages`** (время обнаружения, восстановления, число попыток); при исчерпании попыток — то же по чатам до следующего успешного прогона проверки. |

## 16. Постановка (к реализации): хвост чата после джиттера

**Цель:** после случайной задержки (**§2**, джиттер) явно учитывать в промпте любые сообщения, появившиеся в чате **после** исходного (триггерного) сообщения пользователя — в том числе от **других участников и других ботов**, если они уже известны этому экземпляру бота.

**Правила:**

- Опорная точка — **`message_id`** входящего сообщения, на которое формируется ответ (исходное сообщение).
- После джиттера из SQLite (**та же** пара `bot_id` + `chat_id`, что и сейчас) выбираются строки, у которых **`message_id` строго больше**, чем у исходного сообщения (хвост чата по порядку id в рамках уже записанных в БД апдейтов). Поле **`reply_to_message_id` в схему не вводить** — не фильтровать по ветке reply, нужен **любой** хвост.
- Выбранный хвост **подмешивается в пользовательский контекст** для LLM (формат согласовать с **`format_recent_for_prompt`**: не дублировать исходное сообщение без необходимости; избежать лишнего роста токенов — при необходимости лимит строк или объединение с существующим окном **`recent_for_llm`**).
- Учитываются только сообщения, которые бот **уже успел получить и записать** в **`chat_messages`**. Произвольно «дочитать чат» с серверов Telegram через Bot API **нельзя**; сообщения, не пришедшие в апдейтах, в хвост не попадают.

**Статус:** в коде по состоянию на версию документа ниже — **не реализовано**; реализация — отдельной задачей.
